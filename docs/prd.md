# Todo MVP PRD

## Summary

Build a minimal multi-user todo web app with a flexible item model. Users sign in with email-based magic links generated in the terminal. Each user currently sees one global todo view, while the data model supports future folders and configurable statuses.

## Goals

- Let any user sign up or sign in with an email address.
- Keep users isolated so each user only sees and changes their own items.
- Store users, sessions, login tokens, nodes, statuses, items, and item status history in SQLite.
- Support creating, editing, changing status, and reordering visible todo items.
- Provide touch-friendly drag controls and Move Up/Down fallback buttons.

## Non-Goals

- Real email delivery.
- Node browsing or node-management UI.
- Status-management UI.
- Tags, offline support, collaboration, or production deployment setup.

## Authentication

- Normalize email addresses to lowercase.
- Create new users as needed and seed `Active`, `Deferred`, `Completed`, and `Archived` statuses.
- Set only `Active` as visible in the todo view and as the default for new items.
- Print one-use magic login links to the terminal. Links expire after 30 minutes.
- Sessions expire after 30 days and logout invalidates the current session.

## Items And Statuses

- Items require a non-empty body and may have an optional title.
- New items are uncategorized with `node_id = NULL`, receive the user's default status, and appear at the top of the todo view.
- Each status has one fixed category: `active`, `deferred`, `completed`, or `archived`.
- Changing an item's status may include an optional note.
- Status changes atomically update the item and append one history row.
- Item creation appends an initial history row from `NULL` to the default status.
- Status history appears newest-first on the edit page.
- Changing an item to a hidden status clears its todo rank and removes it from the todo screen.
- Reactivating an item generates a fresh top rank without changing the intentional-reorder timestamp.
- Folder movement changes only `node_id`; folder UI is deferred.

## Ordering

- Visible todo ordering uses string ranks generated by `fractional-indexing`.
- New and reactivated items receive a fresh top rank.
- Dragging sends only the moved ID and its adjacent IDs.
- The server verifies ownership, visibility, and adjacency before generating a new rank.
- Dragging and Move Up/Down update only the intentionally moved item's `todo_rank`, `todo_rank_changed_at`, and `updated_at`.

## Data Model

### `users`

`id`, `email`, `created_at`

### `login_tokens`

`id`, `user_id`, `token_hash`, `expires_at`, `used_at`, `created_at`

### `sessions`

`id`, `user_id`, `session_hash`, `expires_at`, `created_at`, `revoked_at`

### `nodes`

`id`, `user_id`, nullable `parent_id`, `name`, `kind`, `created_at`, `updated_at`

### `statuses`

`id`, `user_id`, `name`, `category`, `show_in_todo_view`, `is_default_for_new_items`, `created_at`, `updated_at`

### `items`

`id`, `user_id`, nullable `node_id`, `status_id`, `kind`, nullable `title`, `body`, `status_changed_at`, nullable `todo_rank`, nullable `todo_rank_changed_at`, `created_at`, `updated_at`

### `item_status_changes`

`id`, `item_id`, nullable `from_status_id`, `to_status_id`, nullable `note`, `changed_at`

## Routes

- `GET /login`, `POST /login`, `GET /auth/magic?token=...`, `POST /logout`
- `GET /`: show visible todo items.
- `POST /todos`: create an item.
- `GET /todos/:id/edit`, `POST /todos/:id`: edit an item.
- `POST /todos/:id/status`: change status with an optional note.
- `POST /todos/reorder`: move one visible item between adjacent visible items.
- `POST /todos/:id/move-up`, `POST /todos/:id/move-down`: reorder fallback.

## Security And Accessibility

- Store only token hashes.
- Treat bodies, cookies, route params, and reorder payloads as untrusted.
- Validate ownership for item, status, and reorder operations.
- Enable SQLite foreign keys for every database invocation.
- Use semantic forms, labels, buttons, lists, and a real dialog.
- Do not rely only on drag and drop for ordering.
